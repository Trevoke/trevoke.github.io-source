* Introduction
In [[./record-driven-development.org][the previous article]], we laid out the general behavior for /The Recs Files/, a record-driven system for agentic development.

In this article, we show you how we use these records day to day on *Stone*, a Racket framework for creating and managing agentic facilities, allowing the user to treat an agentic run as a governed job (bounded, portable, auditable, and supervised). Every example below is pulled directly from Stone's repository.

A word before we start. For teamwork, or any serious work, we highly recommend the records be written by hand[fn:1].

* Repository Layout & The Context Budget

The repository layout follows /The Recs Files/ - see the previous article for the explanation:

#+BEGIN_EXAMPLE

CURRENT_VOCABULARY.md          ← Inlined whole

deferred.md                    ← Decisions deliberately not made yet

plans/                         ← Dated implementation plans
#+END_EXAMPLE

** Managing the Context Budget

Every session starts by reading =AGENTS.md=. This pulls in =VISION.md= and =CURRENT_VOCABULARY.md= in full, but loads every other record file *by title only*.

This title-only listing forms a compact projection (a few hundred lines) that informs the agent of what records exist. The text of a record is read from its own file *only* when active work touches it. System instructions enforce this explicitly:

#+BEGIN_QUOTE
Open a record's file before you cite a section of it, measure code, a test, a plan or a design against it, assert its text, propose a change to it, or frame a question to the user with it. Its title tells you which records bear on the work; it is never the evidence that something conforms.
#+END_QUOTE

** Order of Precedence

When evaluating new ideas or resolving conflicts, decisions walk a strict precedence hierarchy:

Vision ⟶ Ubiquitous Language ⟶ User Workflows ⟶ Features / ADRs ⟶ Error Messages

* Anatomy of the Record Categories

** Vision: The Ultimate Tie-Breaker
Stone's vision defines the core boundaries and costs of the system. The most crucial section for governing AI agents is /What is deliberately not here/:

- No agent marketplace, no prompt library, no model zoo.
- No hidden retries or silent fallbacks. Everything that spends is metered and appears in the log.

Defining a vision requires saying yes to some things and no to everything else. Saying 'no' here is an important way to exclude ideas from even showing up in conversation, let alone in code.

** Ubiquitous Language: The Words Underneath Everything
The ubiquitous language bounds every other record and conversation. Stone adopts NIST's manufacturing control taxonomy (devices, machines, process plans, production plans).

Rules for managing domain terms:

- Define a thing through what it is, not what it isn't :: Just as in the vision, you can't define purely through exclusion, you have to say 'yes' to something first.
- No new word enters any file without explicit human agreement :: This feels painful at first but is a highly valuable exercise in discipline.
- When a word changes, change it everywhere in one commit :: Docs, code, comments, and tests in a single commit.

** User Workflows: Where Every Conversation Starts
Written in Alistair Cockburn's casual use-case form, workflows describe actor goals. We have not yet felt the need to explore more structure, but we believe that gherkin-style text may be valuable here, as these records come close to describing acceptance tests.

#+BEGIN_EXAMPLE
,* UW-2 Get a long job done without watching it
:PROPERTIES:
:LEVEL: user goal
:ACTOR: Operator
:END:

, Main success scenario

1. Operator writes a facility holding shared resources and a production plan binding capabilities (F-9, F-28).
2. Operator declares subscribers (F-13, F-21).
3. Operator releases a job and stops watching.
, Extensions
,* 2a. A subscriber cannot be built :: The job runs without it, and the release notes it (EM-27); subscriber behavior cannot affect job execution (F-13).
#+END_EXAMPLE


- The extensions are where the real work lives :: Main scenarios are easy consensus; extensions define edge cases and cite the corresponding feature or error record.
- Questions must be framed through workflows :: Agent inquiries must open with the workflow and clause being addressed before discussing technical mechanics.


** Features vs. Architectural Decisions
- Features (=F-n=) :: Describe the surface area—inputs, outputs, and user rules. We use plain text, but here again, gherkin structure (features, scenarios, example mapping) may be more valuable.
- Architectural Decision Records (=ADR-n=) :: Formalize mechanisms, constraints, and invariants using Nygard's format (Context, Decision, Consequences).

To prevent the agent from misfiling decisions, we enforce two placement tests:

1. *Verb/Sequence Test:* If describing the record requires a verb, argument, or step sequence, it is a **Feature**, not an ADR.
2. *Implementation Survival Test:* If a word survives an implementation swap, it belongs in **CURRENT_VOCABULARY.md**. If changing implementation retires the word (e.g., "middleware"), it belongs in an **ADR**.

** Error Messages: The Exact Words
Concrete refusal and failure strings are stored in the error messages category (=EM-n=):

#+BEGIN_EXAMPLE
,* EM-27 A subscriber that raises as it is built is left off, and the job runs on
: release: subscriber build failed: "logger-1" raised "connection timeout"
#+END_EXAMPLE

Because these messages serve as diagnostic interfaces for humans and feedback loops for plan-authoring agents, we also decided that *tests assert error messages in full*, never via regex or substring matching.

* The Workflow
Work moves through three phases, each driven by a skill. What follows is the short version; the skills themselves are in [[https://github.com/Trevoke/the-recs-files][the-recs-files]] if you want the full detail.

** Phase 1: Brainstorming
- Read the records first, then refine the idea with the human one question at a time, always citing records by number and title.
- Propose 2–3 approaches, then present the chosen design in short sections, each approved before moving on. New terms are discussed but enter no file until the human agrees to them.
- Route each agreed decision to its record type (workflow, feature, ADR, vocabulary, error message) and propose the change along with whatever it would make false. Records are written only at the human's direction.
- Implementation-only leftovers go into a dated design doc, which code may never cite.

** Phase 2: Writing the Plan
- Write a plan for an engineer with zero context: exact paths, complete code, exact commands and expected output, and each task citing its records.
- Every plan carries four mandatory sections: the vocabulary terms in play, the files it may not modify, the records to read first, and error text settled before the test that asserts it.
- Each task is a test-first cycle: failing test, see it fail, minimal code, see it pass, commit.
- If the plan and a record disagree, the record wins: planning stops and the disagreement goes to the human.

** Phase 3: Subagent-Driven Development
- Each task goes to a fresh implementer subagent, given the full task and record text. It can ask questions, then implements test-first, commits and reviews its own work.
- Two read-only reviewers check the task's commits in turn: first against the spec and records (error text must match exactly), then for code quality. Any finding goes back to the implementer and is re-reviewed until approved.
- Implementers run one at a time, since a worktree has one git index. No subagent ever edits a record, and a record conflict goes to the human.
- A final review covers the whole branch before it's finished.

** Pointers & Traceability Anchors in Code

In code, comments exist purely as citations pointing back to decision records or knowledge-base files:

#+BEGIN_SRC racket
;; EM-27: A subscriber that raises as it is built is left off, and the job runs on
;; UW-2 §Extensions 2a: Get a long job done without watching it
;; EM-24: Anything a machine raises becomes a machine fault
(define (say-a-subscriber-was-not-attached a-subscriber raised)
...)
#+END_SRC

** Pulling The Red Cord
A failing test is not a reason to stop: it is the normal state of a test-first cycle, and the implementer (or a dedicated fix subagent) handles it.

A contradiction with a record is. When a plan disagrees with a record, or a task could only be completed by changing one:

1. *Halt:* Work stops at the point of disagreement. Nothing is planned or coded around the record, and no agent "fixes" the record to fit.
2. *Yield Control:* The disagreement goes to the human.

The human resolves it, either by correcting the plan or by amending the record. Records change only at the human's direction.

* Heuristics: What Belongs in a Record?

Left unguided, agents tend to turn every local helper function into a record. To keep the projections useful, we gather a strict set of heuristics:

** The Core Rule
#+BEGIN_QUOTE
A record is anything worth a team-level decision. If a teammate (or agent) implemented this differently, would you want to have agreed on it first?
#+END_QUOTE

** What Belongs in a Record

- User Workflows (=UW-n=) :: What the user is trying to achieve and what happens when an edge case occurs.
- Features (=F-n=) :: Surface area rules, combinator syntax, and input/output expectations.
- Architectural Decisions (=ADR-n=) :: Non-obvious trade-offs, retry/metering strategies, and resource boundaries.
- Error Messages (=EM-n=) :: Exact sentences an operator reads when a release or step fails.
- Ubiquitous Language (=CURRENT_VOCABULARY.md=) :: Terms with wide reach across modules, messages, or records.

** What Does NOT Belong in a Record

- Local Implementation Mechanics :: Helper function splits, local variable names, or loop constructs (handled in code review).
- External Facts :: Technical quirks or facts about third-party libraries (these belong in =knowledge-base/=).
- Uncommitted Decisions :: Decisions not yet made belong in =deferred.md= as =DEF-n= items rather than binding code.

** Structural Rules for Records
-  The Headline Test :: If you cannot write a single title that clearly states the decision, you either have no decision yet or you have two.
- One Reason to Change :: Split records containing "or" conditions into discrete records to prevent half-true specifications.

* Conclusion

/The Recs Files/ enables a workflow with a clear separation of informational concerns:

#+BEGIN_EXAMPLE
[ Brainstorming ] ──► [ Records (UW, F, ADR, EM), human-approved ]
│
▼
[ Implementation Plan ]
│
▼
[ Subagent Execution + Review ]

Any record contradiction, at any stage ──► [ Halt, yield to human ]
#+END_EXAMPLE

This enables us to move closer to congruence over time, because it reveals incongruence faster.
